# 排版标准：只做覆盖范围内能稳住的

| 项 | 内容 |
| :-- | :-- |
| 对应 PRD | [ai-document-delivery-prd.zh.md](./ai-document-delivery-prd.zh.md) |
| 依据 | 打开试验 + [网上能找到的规则](./tencent-doc-layout-literature.zh.md) |
| 通道 | `doc create` / `overwrite` 的 `content_type=markdown`（已证明会编成标题、列表、表、加粗） |
| 不是 | 飞书文档、Word 精排、模板库、开发任务 |

飞书好看，靠编辑器组件和样式系统。我们交给腾讯文档的门更窄。产品设计必须先认这扇门，再在门里把编排做对。做不到飞书，不是失败条件；在门里仍交草稿，才是失败。

---

## 1. 设计立场

**在 markdown 能落下的结构里，把阅读做对。**

不承诺：字号、段间距、对齐、下划线、主题色、高亮块、分栏、画板、图片。那些工具栏有、这条写入没有。拿它们和飞书比，只会设计不下去。

承诺：打开后是标题、正文、列表、表格各就其位的文档，没有对话腔，没有语法展览，敢把链接发出去。

---

## 2. 覆盖范围（已用试验证明）

| 用 | 不用（本通道不稳或像展览） |
| :-- | :-- |
| 页眉当题目 | 正文再写一遍同名 `# 题目` |
| 章节标题最多两级（`##` / `###`） | 标题三以下、一屏里堆六级 |
| 短段落、空行分段 | 一堵墙；或一句一段碎成通知 |
| 短并列 → 列表 | 叙述、分析拆成满篇 bullet |
| 行列对照 → 一张表 | 把表写成很长的句子；或为了有表硬造表 |
| 偶尔 `**加粗**` 一个词 | 整句加粗、斜体删除线挤一句 |
| 必要时一句引用、一条分割线 | 每节一条线、满篇引用 |
| 技术材料里短代码 | 任务列表 `- [x]` 冒充待办 |

依据：飞书「标题只给章节、默认成段」；clreq「大标/中标/小标，不是六级都用」；我们自己的打开试验。

---

## 3. 三种去向，同一套结构纪律

去向决定写什么，不决定另做一套皮肤。结构纪律相同，取舍不同。

**介绍 / 对内说明**

页眉是名字。正文：这是什么（一段）→ 解决什么 → 现在怎样 → 从哪开始。列表只给「从哪开始」那种短步骤。

**给机构**

页眉是材料名。正文：为何值得看（一段）→ 能提供什么 → 不做什么（可表）→ 下一步。不写仓库、不写内部函数名。

**给开发者**

页眉是技术题目。正文：它是什么（极短）→ 如何跑（列表）→ 关键约束（表）→ 常见失败。代码只放真正要敲的，不当装饰。

**文章**

几乎不用表。两级章节都慎用。连贯段落为主。

---

## 4. 怎样算「在范围内已经排好」

打开后同时成立：

1. 题目只出现在页眉；
2. 章节名在说事，不在说「标题二」；
3. 能扫读：先主张，再块；
4. 该表是表，该列表是列表，其余是段落；
5. 没有「好的我来整理」、没有残留 `#` `-` `**` 当字符（那是走了 text 通道）；
6. 你愿意把链接发给说好的那种人——即使它没有飞书的高亮和分栏。

第 6 条是产品验收。做不到飞书视觉，但第 6 条成立，设计就成立。

---

## 5. 明确不设计的

- 不追飞书高亮块、分栏、画板；
- 不把 Kami / PDF 纸面风格搬进腾讯文档；
- 不在 markdown 里模拟字号和对齐；
- 不把「工具用全」写成质量。

若将来节点编辑或 docx 导入能稳定做标题级别、图片，再扩大范围。现在不把未覆盖的写进标准。

## 7. 给后面技术方案的一句话

编排输出必须是**遵守本文纪律的 markdown**，写入必须走已验证会解析的通道，禁止默认 `text`。标准先定，实现后跟。
